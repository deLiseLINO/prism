# Providers

The Providers view is the CRUD surface for daemon providers: wires, endpoints, models, credentials, enablement, and pool policy. Every write goes through the generation CAS.

## Sub-features

- List: a rail (`aside.prov-rail`, one `.prov-prow` per provider with id, enabled toggle, wire label, and a count of enabled models) beside a detail pane (`.prov-detail`) for the active provider. The rail shows no disabled-model count; the detail pane keeps the `N off` count. The detail head shows id, wire label plus base URL, and an Enabled/Disabled toggle. Wire labels are `openai-completions` (chat), `openai-responses` (responses), `anthropic` (messages), `cline`; codex and antigravity show their raw name. The generation stays in component state for CAS writes and is not rendered. Credential state is deliberately not rendered anywhere in the providers UI (rail, detail, editor).
- Create: `POST /api/v1/providers` with `{id, wire, ...}`; wires are `codex`, `antigravity`, `responses`, `messages`, `chat`, `cline`. The editor offers only the four in the wire picker (`openai-completions`, `openai-responses`, `anthropic`, `cline`).
- Replace: `PUT /api/v1/providers/{id}` with `expectedGeneration`; absent fields preserve existing values (absent=preserve merge).
- Delete: `DELETE /api/v1/providers/{id}?expectedGeneration=N` cascades in one generation write. It removes routes and aliases whose value starts with `<id>/`, drops that provider's combo targets, deletes combos left with no targets, then deletes the stored credential. Returns 200. The UI Delete button opens an inline Confirm ("Delete <id>?", confirm label `Delete`).
- Rename: `POST /api/v1/providers/{id}/rename` with `{to, expectedGeneration, dryRun}` gives a provider a new id in one generation write. It rewrites every config field that names the old id: combo targets, route and alias keys and values (`<id>/<model>` and `claude-<id>--<model>`), the vision sidecar target, pinned and catalog accounts, and a legacy `<id>:default` key reference. It appends a record to the `providerRenames` ledger in the config. The daemon then moves this machine's data: credential directories (moved, never copied) and account metadata, so accounts keep their state, and usage history recorded before the rename (attempt providers and request model ids). Integrations Prism manages pick up the new model ids from the config change. The old model ids stop resolving; there is no alias for them. A crash after the config write finishes the move on the next start or reconcile, and repeating the request answers `alreadyApplied`. `dryRun` returns the plan (`configRefs`, `accounts`, `usageAttempts`) and warnings and writes nothing.
- Rename conflicts change nothing and answer 409 `rename_conflict` with every reason in `conflicts`: `not_found`, `invalid_id` (ids use letters, digits, `_` and `-`, with at least one letter or digit; provider create uses the same rule), `same_id` (also a case-only change), `reserved_login_id` (`codex`, `antigravity` and `cline` cannot be renamed or used as targets), `provider_exists`, `dir_collision` (the new id maps to another provider's credential directory), `model_shadowed` (a route, alias or combo key already claims a model id of the new id), `credentials_orphan` and `accounts_orphan` (data of an earlier provider with the new id is still on disk), `auth_in_progress` (a sign-in for the provider is open), `rename_in_progress`. A move that fails after the config write answers 500 `rename_incomplete`; the daemon keeps the provider unbuilt and retries on every reconcile.
- Not moved by a rename: the in-memory request journal (Logs), quota probe times and pool counters, integration rollback journals, orphan credential directories, the model catalog cache, and hosts on older builds or with auto sync off. Client configs written by hand with `<old>/<model>` or `claude-<old>--<model>` must be updated by the user. Usage recorded after the rename under the old id (requests that failed to resolve) keeps the old model string.
- In the UI, the ID field of `Edit provider <id>` renames the provider. Each changed id gets a dry run after a short pause, and a `What the new id changes` section lists the model id change, config references, accounts moved, usage attempts, and the warnings. A refused id shows `Rename blocked, nothing changed` with every conflict, and `Save changes` stays disabled until the current id passes the check. Save runs the rename first, then saves the other fields under the new id only when they changed.
- The CLI runs the same endpoint: `prism providers rename <id> <new-id> [--dry-run] [--json]` prints the plan and warnings, or every conflict with exit code 4. The TUI action menu has `Rename provider` (`m`), which picks a provider, then checks the typed id with a dry run before it renames.
- Synced machines: the ledger travels in the pushed config. Before merging, each machine replays the records it has not applied and whose old id it still has, through the same config write and data move, so its own sign-in accounts and usage history follow the provider and no old provider stays beside the new one. A replayed record keeps its id and takes the machine's own time. A rename the machine refuses fails the sync with the same 409 body until the conflict is fixed. Ledgers merge as a union, so a push from an older build without a ledger keeps the machine's records.
- Credentials: paste-once write (`credential` in the write body, or `apiKeyRef`); reads show only masked state (`set`/`unset`) in the API; the value never round-trips and the UI never renders the state.
- A credential replacement stages a private immutable key reference before publishing the generation-checked provider config. Failed staging, config persistence, or stale CAS leaves the active key, config, and account policy unchanged. Rejected accounts resume only after successful replacement; explicit user pauses remain paused, including after restart. Old-key failures cannot reject a newer generation.
- Unpublished immutable key revisions may remain after a failed config write. They are not active credentials and have no automatic garbage collection. Provider deletion and credential cleanup remain separate operations.
- Dispatch requires the published disk config, selected key reference, and credential generation to agree. Legacy generation-1 keys and valid UUID references remain readable. The API cannot roll credentials back by assigning an arbitrary old reference; replacement publishes through the write-only credential field.
- The daemon adopts a valid `prism.json` changed outside it on the next request, whether or not the generation moved. The request that notices the change still runs on the old settings; later requests use the new ones. A changed `apiKeyRef` is not dispatched until the next reconcile pass (at most 10s) publishes it. A file that no longer parses or validates keeps the last good config and is logged once; an unreadable file blocks dispatch until it can be read.
- Clearing an already published `apiKeyRef` returns 400. Initial anonymous providers and valid legacy activation remain supported. Credential observers retain the acquired user-policy version while reporting the credential generation actually dispatched.
- Changed-key recovery persists account policy before changing runtime state. A failed policy write after config CAS returns 500 `credential_publication`; config is already committed, while runtime remains fenced. Publication can retry in the same process after storage recovers. Restart in this failed partial-commit window does not automatically recover the rejected account.
- Delayed login registration preserves pause, priority, and a rejection recorded for the new credential generation. A rejection of the replaced generation does not prevent successful login recovery. Cline refresh 401 and 403 are permanent credential failures; 429 and server errors remain transient.
- Enable/disable: the Enabled toggle in the detail head or the rail row PUTs `enabled`. Per-model toggles edit `disabledModels`. Detail also has Disable all and Enable all buttons (`aria-label` "Disable all models" / "Enable all models") and an `N off` count.
- Editor (`ProviderModal`, dialog `New provider` or `Edit provider <id>`) has exactly four fields: ID (`#prov-id`; when editing, a changed id renames the provider as described above), Wire (segmented buttons in `role=group` "Provider wire"; hidden `select#prov-wire`; editing an unknown wire shows a badge instead), Base URL (`#prov-base`), API key (`#prov-cred`, password, placeholder `paste key`). When editing, Base URL and API key both hint `Empty keeps the current value.`. Footer buttons are Cancel and `Create provider` / `Save changes`. Create is disabled while ID is blank, or while the wire is `responses`, `messages`, or `chat` and Base URL is blank (unless the existing provider already has one). Save re-sends the existing models, disabledModels, syncedModels, pool, and modelSettings unchanged. Default models, Models, Disabled models, credential reference, and the Enabled toggle are not in the editor.
- Adding models: the detail has an add line (`.prov-addinput`, placeholder `model id, e.g. gpt-5.3`) with Add and Configure (opens the model settings modal for a new id). Both disable when the id is blank or already listed.
- Cline catalog: a `free`/`pass` segmented control (`role=group` "Cline catalog") appears in the detail only for cline providers.
- Search: `#provider-search` (placeholder `Filter by id, wire, or model`) filters the rail by provider id, wire, or model.
- Model mode switch (antigravity only): `PUT /api/v1/providers/{id}/model-mode?expectedGeneration=N` with `{"mode":"raw"|"logical"}` moves the stored `models` list between collapsed family ids and raw wire ids in one generation write. Disabled entries and per-model settings travel with their model (family state fans out onto members in raw mode, folds back onto the family id in logical mode). The catalog, routes, and agent integrations observe the new list on the next read; nothing else to re-apply. Non-antigravity wires get 400 `invalid_value`.
- Sync: `POST /api/v1/providers/{id}/sync-models` replaces previously listed models with discovery results and preserves manual models absent from the previous `syncedModels`. Antigravity catalogs belong to one provider and endpoint, persist across restart, and drive both logical and raw routing. Removed models lose associated settings and exact references; retained models keep their settings. Failed discovery writes nothing.
- Connect link: `prism://connect?v=1&id=<id>&wire=<responses|chat|messages>&endpoint=<url>[&endpoint=<url>...][&mode=spread][&model=<id>...][&defaultModel=<id>]&key=<secret>` describes one provider. The first `endpoint` is the base URL and the rest are fallbacks. A link is at most 8192 bytes; an unknown or repeated single-value parameter, a fragment, or a non-http(s) endpoint is refused with 400 `invalid_link`, and no error quotes the link. A link never overwrites a provider: an existing id is 409 `already_exists`. A link without models runs discovery after the provider is saved; failed discovery keeps the provider and returns `warning`.
- Web form of a connect link: `https://<host>/connect#<parameters>` carries the same parameters after `#` and is accepted wherever the `prism://` form is. A query on the page URL, another path, user info or an empty fragment is refused with 400 `invalid_link`. The page `worker/connect.ts` serves at `/connect` never receives the fragment; its script opens `prism://connect?<parameters>`, offers the latest release downloads for macOS, Windows and Linux, and copies the `prism://` link.
- Three entry points share `POST /api/v1/connect`: `prism connect <link>|--stdin [--dry-run] [--json]`, the desktop app as the handler of the `prism` scheme (cold start, a second instance, and macOS `open-url`), and `Add from link` beside `New provider`. The desktop dialog `Add provider from link` runs a dry run first and lists id, wire, every endpoint with the first marked `primary`, mode, models and the masked key; nothing is written until `Add provider`. A link opened from the operating system targets this machine; a pasted link targets the machine being managed, and the dialog names it when it is remote. The key appears only as a four-character preview.
- Existing models with no recorded sync provenance are preserved. Older syncs discarded provenance for models that had already disappeared, so those entries cannot be distinguished from manual additions and require manual removal.
- Catalog fallback: when a model has no manual window and no listing window, the daemon fills the window from a public catalog cache. Each catalog provider casts one vote. A provider that disagrees with itself abstains. The value with the most votes wins when that count is unique. A tie stays unknown. Listing facts and manual settings still win, including a listing that said the model is text-only. Image uses the same vote. The modal caption uses `resolvedFacts.contextSource` (`listing`, `catalog`, or `global`) and does not recompute that chain.
- Catalog efforts: the catalog effort ladder is voted the same way, as one ordered set per provider. Rungs are normalized to `minimal, low, medium, high, xhigh, max` (catalog `none` and unknown rungs drop). A manual `reasoningEfforts` list wins. Otherwise the winning catalog ladder feeds client configs. `resolvedFacts.efforts` and `resolvedFacts.effortsSource` (`manual`, `catalog`, `none`) show the result.
- The Providers detail renders the stored list in both modes with the same rows: toggle, edit, remove buttons, fresh badge, and effort rungs. Rungs render only for models with manually overridden `modelSettings.<model>.reasoningEfforts`; a model without an override shows no rung row. The `manual` badge marks ids the last sync did not report; an absent `syncedModels` list marks none.
- Per-model API: `modelSettings.<model>.wire` (`responses`, `chat`, or `messages`) overrides the provider wire for that model only. The provider keeps one base URL and one credential. Only providers whose own wire is `responses`, `chat`, or `messages` accept it; codex, antigravity, and cline providers reject it with 400. `resolvedFacts.<model>.wire` and `wireSource` (`model` or `provider`) report the effective value. The model settings modal shows an "API" section for those providers, and the model row carries a wire tag when the override is set. Picking the provider's own wire in the modal stores no override.

## How to get to it (user POV)

Click `Providers` (`#/providers`). `New provider` opens the four-field editor. Click a rail row to select a provider; its detail pane has the Enabled toggle, model list with per-model toggles, Sync (`Refresh models from provider`), Disable all / Enable all, the add-model line, Edit, and Delete. Antigravity providers with families also show a `raw models` / `logical models` button.

## Driving it with the harness

```sh
bash verify/scripts/desktop-controls.sh
bash verify/scripts/prismctl-proof.sh
bash verify/scripts/api-sweep.sh
bash verify/scripts/model-mode-proof.sh
```

`desktop-controls.sh` proves the current UI path for create, per-model toggle, and delete of a throwaway `ui-probe` provider through real clicks. It does not currently prove Edit, the provider enabled toggle, credentials, cline catalog, or search. `prismctl-proof.sh` exercises the CLI mutation ladder; `api-sweep.sh` proves POST/PUT/DELETE and a stale-generation 409; `model-mode-proof.sh` proves the logical↔raw switch round trip through the real UI button, the stored config, and the catalog.

Every mutation uses throwaway provider ids (`ui-probe`, `openai-proxy`), never the user's `codex`/`antigravity`, and cleans up in the same run. Never write credentials for the user's real providers during verification.

## Gotchas

- Generation CAS: every write needs the current `expectedGeneration`; a stale value returns 409 `stale_generation`, not a silent overwrite. The UI surfaces a re-fetch button on that error.
- Do not edit `~/.prism/prism.json` by hand while the daemon runs. Change providers with `prism providers edit|add|enable|disable|remove`, for example `prism providers edit <id> --endpoint <url>`. These commands validate the change and go through the generation CAS; a hand edit skips both, and a broken one is ignored until it is fixed.
- Deleting a provider never fails on references. It succeeds with 200 and cascades to routes, aliases, and combos (see Delete). A proof that seeds a route or combo pointing at the provider must assert those entries are gone afterward.
- A rename proof must send a request under the new id and check Stats: models and usage move to the new id, and `<old>/<model>` must answer an error, not the old provider. Rename throwaway providers only; renaming the user's provider breaks their hand-written client configs.
- The credential field is write-only: asserting it "round-trips" is wrong by design; assert `credential.state === 'set'` after a write and `unset` after delete through the API. The UI does not render the state anywhere, so a proof must assert its absence in the DOM (no `.prov-prow-sub .badge`, no credential badge in `.prov-detail`, no `Already set` hint in the editor) rather than a rendered value.
- Editing an existing provider from the UI keeps its model list, since the editor has no Models field. Change models through the detail pane (toggle, add, remove, Sync) or the API.
- `responses`/`chat` wires require a Base URL in config validation, doctor, and the API (400 `invalid_value`). The editor also blocks `messages` without a Base URL, which the API allows.
- The wire picker labels differ from wire ids (`chat` is `openai-completions`, `messages` is `anthropic`). Drive it by the label text or the hidden `select#prov-wire` value.
