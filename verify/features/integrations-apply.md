# Integrations apply and rollback

The Integrations screen writes client configuration for Codex, Grok, OMP, Claude, Pi, opencode v1, opencode2, and Hermes. The user-facing contract includes the button state, the action, the refreshed badge, the rendered error path, and the file written on disk. Calling `window.prism.integrations.apply()` directly does not cover that contract.

## Sub-features

- The navigation button opens the Integrations screen.
- Each installed client renders an enabled Apply button; Rollback is disabled until managed.
- Apply changes the same card from `unmanaged` to `managed`; Rollback returns it.
- Apply writes a client configuration the real client can parse: Codex `[model_providers.prism]` in `~/.codex/config.toml` plus the root routing pair — a `# Managed by prism` marker and `openai_base_url = http://127.0.0.1:<port>/v1` at the document root, so the built-in `openai` provider routes through the daemon even when another config manager had injected its own pair: the foreign pair is displaced and journaled (`# prism-routing` lines inside the fence) and rollback restores it verbatim — plus the model catalog pair: a second `# Managed by prism` marker with root `model_catalog_json = <codex home>/prism-catalog.json` and the rendered catalog file itself, so the Codex model picker lists the daemon's `provider/model` slugs instead o…
- opencode v1 and opencode2 share one file and must coexist: v1 owns the `provider` (singular) key, v2 owns the `providers` (plural) key, and a rollback of either leaves the other untouched.
- Rollback removes the Prism-owned configuration without changing user-owned bytes; a rollback of an unmanaged file is an honest refusal.
- Each card carries an `Auto-apply` toggle. Off by default. The toggle persists daemon-side in `prism.json` (`integrations.<id>.enabled`) and survives a daemon restart. Toggling is a generation-checked write (`PUT /api/v1/integrations/{id}/enabled` with `expectedGeneration`); a stale generation triggers one refresh-and-retry, then an honest refusal.
- With the toggle on, every daemon config change (providers, models, port) re-applies the client config through the daemon's watcher with no UI action. Refusals are logged to `app.log` as `prismd: auto-apply <id>: <reason>`; success is silent.
- A damaged managed block refuses Apply and preserves the file byte for byte. On a damaged card the Auto-apply toggle stays operable (enablement is config, not file state) while Apply and Rollback are disabled; the auto-apply watcher refuses on the same damaged file and also leaves it byte-identical. The logged reason is the collision formulation (the orphaned fence makes the old prism tables indistinguishable from user tables, so the collision guard fires before the fence guard), not the `fence is damaged` string — assert any honest `prismd: auto-apply <id>: prism:` refusal on fresh log lines plus the byte-identical file.
- Drift: a managed block pointing at a different endpoint renders a `drift` badge.

## How to get to it (user POV)

Launch Prism, click `Integrations` in the left navigation, find the card headed `codex`, `grok`, `omp`, `claude`, `pi`, `opencode`, `opencode2`, or `hermes`, then click Apply. The card must display `managed`. Clicking Rollback must return it to `unmanaged`.

## Driving it with Electron CDP

Use `scripts/integration-drive.sh` for Apply. It clicks the rendered navigation and Apply buttons for all eight clients, never substituting a preload call for the click. The same script covers the Auto-apply toggle: it clicks the grok card's toggle through the rendered `label.toggle`, then proves the watcher with a provider `PUT` that adds a model and lands the derived alias in the grok config with no UI action, breaks the grok fence to assert the damaged-card button states and the auto-apply refusal line in `app.log`, repairs the fence, then kills the daemon process and requires the supervisor relaunch to re-apply the enabled grok config and still report `enabled` on `GET /api/v1/integrations`. Use `scripts/desktop-controls.sh` for the Rollback path: it clicks Apply on the grok card, waits for the `managed` badge, clicks Rollback, and requires the badge to become `unmanaged` — all through the rendered buttons.

For every client, assert all four facts:

1. Apply is enabled.
2. No alert appears after the click.
3. The card renders the exact `managed` badge (and after Rollback, exactly `unmanaged`).
4. The expected file exists in the isolated client home and points to the verification daemon.

Then run the real clients with the isolated home: `grok models` and `omp models` must list prism entries; `claude doctor` must not report `Invalid settings` (a broken settings.json is reported there) and must acknowledge the custom ANTHROPIC_BASE_URL; `pi --list-models` must list a `prism` provider row; `opencode models` must list `prism/` models; `hermes config get providers` must resolve the prism provider and `hermes config check` must not print `Failed to parse`. A marker in the file is not sufficient if the owning client rejects the syntax or reads a different path.

opencode2 beta-19086 has no headless parse probe: `opencode2 models` is a silent no-op in an isolated home and `opencode2 serve` boots even on a broken config. The structural run asserts its file contract (valid JSON, `providers.prism` with the package adapter and the daemon endpoint) and records the skip in `opencode2-models.txt`; real use is covered by live mode against the user's background service.

## Gotchas

- Create the client directories before Electron starts. Installation status comes from the target file or detection-directory existence.
- The Auto-apply toggle's checked state only flips after the renderer refreshes; the toggle is a controlled checkbox. The drive asserts the flip with no remount, no tag loss, and no entry-animation replay.
- The damaged card renders only after a status refresh: navigate away and back, or trigger any `onChanged` action. Asserting damage on a stale card is a bug in the assertion. The renderer derives damage from the fence detail (`detail` mentions fence + damage), while the auto-apply watcher's logged refusal on a damaged grok file is the collision formulation, not the fence-damage string.
- The daemon-restart proof kills the daemon process directly (`pgrep -f <rundir>/prismd`). Electron survives, the supervisor relaunches the daemon, and `watchIntegrations` re-applies every enabled integration at startup. The new daemon's `GET /api/v1/integrations` must still report `enabled` for the toggled client.
- Auto-apply derives Grok aliases from `provider/model` ids: model `gpt-5.6-luna-probe` on provider `codex` lands as `prism-codex-gpt-5-6-luna-probe` (non-`[A-Za-z0-9_-]` runs collapse to `-`). Assert the derived alias, not the raw model name.
- `GROK_HOME`, `CODEX_HOME`, and `PI_CODING_AGENT_DIR` are process-start settings. Changing them after launch does not move the target.
- Direct bridge calls bypass disabled buttons, stale React state, click-handler failures, and error banners.
- OMP may choose `models.yaml` when that spelling already exists. The clean sandbox uses `models.yml`.
- A successful Apply does not prove inference. Run the client compatibility feature in live mode.
- Claude's base URL carries no `/v1` suffix: Claude Code appends `/v1/messages` itself. Asserting a `/v1` endpoint for the claude card is a bug in the assertion, not the apply.
- opencode v1 and v2 share `~/.config/opencode/opencode.json`; an apply of one must never disturb the other generation's key, and each rollback must leave the sibling block intact.
- `claude config list` fatals on the `claude-` alias (never in their model catalog); use `claude doctor` instead: it exits 0, never reports `Invalid settings` on a valid file, and prints `custom ANTHROPIC_BASE_URL` — direct proof Claude Code read the Prism endpoint.
- Claude Code's model catalog gate fatals on `claude-` aliases in print mode (`claude -p`) until its gateway model cache exists. The claude apply therefore seeds `~/.claude/cache/gateway-models.json` (schema: `baseUrl` + epoch-ms `fetchedAt` + `models` id/display_name list, ids must match the CLI's `^(claude|anthropic)` filter) and sets `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`. A cache already pointing at the daemon's endpoint is left untouched (the CLI refreshes it from `/v1/models` itself); a cache belonging to another endpoint is a named refusal. Rollback removes the cache only when it points at the daemon. Without the cache, a cold `claude -p --model claude-...` hangs — that hang is the regression signal for this contract.
- The daemon lists every enabled `provider/model` as a `claude-<provider>--<model>` entry on `GET /v1/models`, and the planner accepts those derived aliases without a configured route. Both are load-bearing for Claude Code: the CLI fetches that list to populate its model picker, and `claude -p --model claude-codex--gpt-5.6-luna` routes without the user pre-creating a route.
- `PRISM_VERIFY_LEGACY=1` seeds the unfenced Prism Grok tables used before managed fences. Apply must migrate them or render a concrete refusal. An empty config cannot cover this upgrade path.
- A Grok apply that would emit an alias colliding with a user-owned `[model.*]` table outside the fence refuses by name before writing — that refusal is a pass for the safety contract, not a failure.
- A codex apply over a user-owned root `openai_base_url` (no foreign managed marker above it) refuses by name before writing, as does a root `model_provider` selecting another provider or duplicate root `openai_base_url` keys — those refusals are passes for the safety contract, like the Grok alias collision. `model_provider = "prism"` switches the apply to provider-table-only: no routing pair is written and a stale prism pair from an earlier routing apply is removed.
- Codex routing ownership survives a config reserialization that strips comments: the fence journal's `# written:` value proves the root pair is prism's, re-apply restores the marker, and rollback still restores the displaced foreign pair. Ownership the journal cannot prove is left in place, never overwritten.
- Codex's model picker never reads `GET /v1/models` for its list — it reads the catalog file named by the root `model_catalog_json` key (codex's own mechanism; other config managers use it too). Without that key Codex lists only built-in GPT models even while routing works. The rendered `prism-catalog.json` entries must carry the full strict field set (`support_verbosity`, `base_instructions`, `truncation_policy`, …) or codex rejects the file with `missing field`; the entries use `shell_type = "shell_command"` with no `tool_mode` and no `multi_agent_version`, because those make codex 0.153 send `exec`/`collaboration`/`image_gen` tools the chat wire cannot carry. A foreign `model_catalog_json` value refuses the apply by name.
- Real codex CLI traffic (`codex exec`) sends request bodies with `Content-Encoding: zstd` — the gzip case comes from some wrappers. The daemon decodes both centrally in `admit` before ingress parsing, caps the decoded stream, and answers unknown encodings with 415. A `responses ingress: invalid_json` on character `(` (zstd magic) means an old binary without this decode is still running: rebuild `apps/desktop/resources/prismd/prismd` and restart.
- The chat-family chat upstream re-announces `finish_reason: "stop"` in several trailing frames (plus a duplicated usage chunk). The chat streamer treats an identical repeat finish as a no-op and still emits one terminal; a *different* second finish reason stays a protocol error. The regression signal for this is a turn that streams its full text and then fails with `run error kind=2 class=7 ... stream ended before a terminal frame`.
- The chat wire renders codex `custom` tool definitions (e.g. `apply_patch`) as plain function tools and drops `local_shell`/`tool_search` definitions — those have no chat-completions representation. Session history items degrade the same way: `reasoning` items and compaction markers are dropped, custom tool calls render as function calls and their outputs as tool messages, so follow-up turns in a codex session work. The codex wire (provider `codex/*`) parses the grammar custom-tool format and drops `tool_search` (the upstream rejects it without deferred tools). The regression signal is `run error kind=2 class=8 accepted=false` on any *second* turn of a session.
- Codex 0.153 tries a WebSocket transport (`ws://…/v1/responses`) whenever it runs on the built-in `openai` provider (root `openai_base_url` routing): the daemon answers 405 and codex burns reconnect attempts each session start before falling back to SSE. Setting root `model_provider = "prism"` (prism's apply then removes the base-url pair) routes through the custom `[model_providers.prism]` table, whose `supports_websockets` defaults to false — no WS attempt at all. The regression signal is `unexpected status 405 ... url: ws://...` plus `Reconnecting... 5/5` at session start.
- Live codex probes need an auth story: with an expired ChatGPT refresh token run `OPENAI_API_KEY=dummy codex exec --skip-git-repo-check -s read-only "Reply with exactly: X"`; the loopback daemon ignores the token. `codex login status` doubles as the config-parse probe (it fails loudly on a catalog the strict parser rejects).
- `/v1/responses/compact` must answer the codex-CLI shape `{"output":[…]}` — `{"id","summary","usage"}` is a console-style shape codex 0.153 cannot replay. Prism renders the compacted history locally (retained items capped to the ~20k-token budget, then a `SUMMARY`-prefixed user message minted by a real summarizer turn through the run machinery) and never puts ids on minted items — codex treats minted ids as modified history. Compaction-family items on the codex wire (`compaction`, `compaction_summary`, `context_compaction`) are normalized once at responses ingress into an opaque user message; an upstream that fails the summarizer turn yields an honest 502 `compact_failed`, never a half-shape.
- `/v1/messages/count_tokens` is answered locally (dedicated parser: `model` required, `messages` optional, no `max_tokens` — which Claude Code never sends and codex-style parsers demand): prism estimates ~4 chars/token and never dispatches upstream, so the probe is a 200 `{"input_tokens":N}` regardless of upstream health. A 400 `missing_field max_tokens` means an old binary is running.
- The chat ingress accepts `max_completion_tokens` (pi/omp/opencode2/hermes send it alongside or instead of `max_tokens`) with max_completion_tokens winning when both appear; the chat egress reports truthful `finish_reason` (`length` for output-token caps, `content_filter` for filtered stops, error-frame-then-abnormal-close without `data: [DONE]` for other incompletes), flushes each frame, and skips a bare `data: [DONE]` marker on replay.
- Claude-wire thinking blocks round-trip through a prism-minted `prismr1:` envelope: routed models have no real Anthropic signature, so the daemon mints one (base64 JSON carrying the thinking text or redacted payload), stores it, and re-emits it on the next turn — Claude Code refuses a resent thinking block with an empty signature. `redacted_thinking` blocks round-trip as opaque data the same way, and a malformed `prismr1:` signature on ingress is a typed 400. `server_tool_use`/`web_search_tool_result` history blocks render as text parts (`[server tool web_search: <query>]` / `[web search results: <urls>]`) so foreign histories stay replayable. The messages egress flushes after every event and pings (~20s) on idle so client idle timeouts never fire.
- A `GET /v1/responses` with WebSocket upgrade headers answers 426 `upgrade_required` (fail-closed; prism never speaks WS) and antigravity truncation is content-gated: a turn whose text or tool args were delivered synthesizes a terminal event; only a turn with nothing delivered emits typed `response.incomplete` — never a bare transport error.
- The chat upstream's `/responses` endpoint can die while its `/chat/completions` endpoint stays healthy (observed 2026-09-07 ~23:58: api.example-upstream.example began 400ing every responses-wire call after account-pool credit exhaustion, chat wire kept returning 200). Every router turn then fails `kind=3 class=8` (Retryable + InvalidRequest) and codex shows `Reconnecting 1/5..5/5` + `stream disconnected before completion` — that looks like a prism regression but isn't; check the tooling log (`~/Library/Logs/com.example.logger/proxy.err.log`) for `proxy /ai/v1/responses ... upstream=400`. The fix is config, not code: switch the router wire to `"chat"` (prism translates both ingresses onto the chat wire). Two rules: never hand-edit `~/.prism/prism.json` for this (the desktop app owns that file through the config manager's generation counter and silently reverts manual edits on its next restart) — use `PUT /api/v1/providers/router` on the daemon port with `{"id":"router","wire":"chat","expectedGeneration":<gen>}`; and the swap lands on the next reconcile tick (≤10s), during which runs on the mismatched wire fail `kind=2 class=8` with no upstream contact. A external session working "through router" is not counterevidence — it routes codex through a different proxy chain to a remote edge endpoint, a different backend entirely.
